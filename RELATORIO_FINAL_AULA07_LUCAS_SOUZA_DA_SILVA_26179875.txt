12 · QUESTÕES DISSERTATIVAS
========================================================================
D1. No Opal, o código é representado pelos prompts, pelas referências com @ e pelas conexões do fluxo visual. O versionamento ocorre no histórico linear do Google Drive, sem branches, diff ou pull request, e os testes acontecem manualmente no Preview e no console. No pipeline como código, Jenkinsfile ou YAML ficam no Git, passam por revisão e executam verificações reproduzíveis. Assim, o Opal acelera descoberta e prototipação, mas prompts aprovados devem ser transferidos para o repositório, revisados e avaliados automaticamente antes da produção.

D2. O fluxo de release notes começa com um User Input obrigatório contendo os commits. Um asset guarda o guia de estilo. O primeiro Generate usa Gemini Flash para classificar rapidamente as mudanças e referencia a entrada e o guia com @. O segundo Generate usa Gemini Pro para redigir o texto profissional, pois exige maior qualidade linguística. As saídas exibem uma página e salvam um Google Docs. Passos recebem nomes descritivos, categorias vazias são omitidas e as conexões não formam ciclos.

D3. O Opal é experimental, não oferece API pública, webhook, exportação de código ou hospedagem própria documentados e possui versionamento linear e testes manuais. Ele não deve ser usado com dados reais ou processos críticos. A equipe promove o mini-app quando a saída chega a clientes, precisa rodar sem pessoa no meio ou exige auditoria. Nesse ponto, fixa modelo e schema no AI Studio, versiona prompt e conjunto dourado no Git e cria gates de CI antes da implantação.

D4. A integração simples com Drive e Workspace facilita o surgimento de shadow IT: apps sem dono, links públicos esquecidos e dados confidenciais copiados em prompts. A política da Carparts deve permitir somente dados públicos ou fictícios, manter inventário com responsável e data de revisão, desativar edição pública, testar entradas de referência e exigir revisão humana. O compartilhamento do arquivo do Drive também deve ser controlado. Experimentos não substituem ferramentas corporativas aprovadas para clientes, pedidos, preços, ERP ou segredos.

D5. O stage de avaliação recebe o prompt versionado e pelo menos dez casos no conjunto dourado. Cada caso verifica termos obrigatórios, termos proibidos, limite de palavras e contrato JSON. O pipeline falha quando a aprovação fica abaixo de 90%. A auth key fica em secret do GitHub ou credencial do Jenkins, nunca no repositório ou no log. Para controlar custo, a avaliação roda apenas quando prompt, schema, casos ou código mudam, usa primeiro um modelo Flash e registra tokens e custo estimado.

D6. O Opal serve para descobrir a necessidade e validar rapidamente a experiência com usuários e dados fictícios. O Chat do AI Studio fixa modelo, instruções e structured output e permite obter código. O Build pode gerar uma aplicação full-stack, manter segredos no servidor e sincronizar com GitHub. O Antigravity ajuda a evoluir o código por pull requests. Jenkins ou GitHub Actions aplicam lint, testes, scan de segredos, avaliação do prompt, homologação e aprovação registrada. A passagem entre etapas depende de valor comprovado, qualidade e governança.
